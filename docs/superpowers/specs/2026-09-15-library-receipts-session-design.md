# MARKA Library, Receipt Fields, and Session Design

**Date:** 2026-09-15  
**Status:** Approved for implementation planning

## Goal

Make image-library deletion truthful and retry-safe, preserve handwritten
student identity on receipts, expose the two answer-sheet downloads, save school
branding once per teacher, and end expired browser sessions automatically.

## 1. Clear Library

The dashboard action becomes **Clear image library**. It permanently removes
every raw and graded proof image owned by the signed-in user, but preserves scan
rows, scores, marks, timestamps, and exports.

The API deletes through the Supabase Storage API in bounded batches. It clears a
database path only after that bucket deletion succeeds. A failed batch remains
referenced and retryable; the response reports deleted and failed counts without
exposing object paths.

The OMR Library displays only scans with a live graded image. Once retention or
manual clearing nulls that path, the card disappears. Result-only rows remain
available to CSV/PDF exports. The dashboard storage figure counts stored images,
not retained result rows.

Individual permanent scan deletion follows the same consistency rule: if an
image cannot be removed, the row remains so the operation can be retried.
Existing unreferenced Storage objects are reconciled once through the Storage
API after deployment.

## 2. Printed student fields

R07-E retains five bounded fields: Name, Student ID, Class, Subject, and Date.
The generator and scanner share one canonical field-coordinate contract. During
printed grading, MARKA aligns the sheet, crops inside each field border, converts
the crop to bounded grayscale WebP data, and attaches it to the stored scan
result.

Receipts reproduce the exact handwriting rather than applying OCR. Name, Class,
and Subject are prominent; Student ID and Date are retained as secondary
details. Missing individual crops render as blank lines. If all crops are
missing, the receipt falls back to the scan ID.

The compact field crops survive proof-image retention and Clear Library, so
receipts continue to work after the larger images are gone.

## 3. Hand-drawn student fields

The reusable A4/40 sheet adds one identity strip between the upper corner
squares and answer grids:

```text
┌──────────────────────────┬──────────┬──────────────┐
│ NAME                     │ CLASS    │ SUBJECT      │
└──────────────────────────┴──────────┴──────────────┘
```

The strip spans 15 cm × 2 cm from 3 cm to 18 cm across the page. Its widths are
8 cm Name, 3 cm Class, and 4 cm Subject. It requires one rectangle and two
dividers, uses whole-centimetre measurements, and is drawn once in permanent
pen.

After anchor rectification, MARKA detects the outer strip and dividers within a
small tolerance, then crops inside the actual borders. If divider detection is
uncertain, fixed canonical insets provide a fallback. Identity-field failure
does not invalidate otherwise safe answer grading; the receipt visibly falls
back to the scan ID.

The construction guide teaches the strip as part of the existing four-step,
one-centimetre method.

## 4. School details and downloadable sheets

Each teacher account stores one sheet profile:

- school or organization name;
- address;
- optional phone; and
- optional email.

A compact dashboard form reads and updates this profile through authenticated
API endpoints. Printed R07-E sheets and receipts reuse it automatically. The
teacher may update the profile before downloading a new sheet; per-exam
overrides and logo uploads are outside this release.

The PDF renderer wraps school name and address to at most two lines each,
shrinks only to a legible minimum, and rejects text that still cannot fit rather
than clipping it. Phone and email share one compact contact line.

The dashboard exposes authenticated downloads for:

- the branded printed R07-E sheet; and
- the generic hand-drawn A4/40 construction guide.

PDFs are generated by the API and streamed directly; ignored local prototype
files are not treated as deployment assets.

## 5. Session expiry

MARKA continues using its backend-issued seven-day JWT. The frontend decodes
only the token's expiry for client-side session timing; authorization remains
server-controlled.

On application startup, an invalid or expired token is removed before rendering
the dashboard. While open, a timer logs out at the expiry instant. Any
authenticated API response with status 401 also clears the token and returns the
user to login. No refresh-token system or new authentication provider is added.

## 6. Failure and security rules

- Storage failures never cause path clearing or row deletion.
- Bulk deletion is scoped by the authenticated user ID on the server.
- Profile fields have explicit length limits and are escaped by ReportLab.
- Handwritten crops are bounded in dimensions and encoded size.
- Logs and API responses contain counts and scan IDs only, never image paths or
  field-image data.
- Destructive actions require explicit confirmation and show partial-failure
  feedback.

## 7. Verification

Automated tests cover:

- raw and graded bulk deletion, partial Storage failure, and retry;
- Library filtering and immediate state refresh;
- expired-token startup, timer expiry, and 401 logout;
- printed and hand-drawn field crop geometry;
- receipt rendering with crops and scan-ID fallback;
- profile validation and long-text PDF fitting; and
- both downloadable PDF endpoints.

Deployment verification checks the live Render API, Vercel asset revision,
Supabase path/object consistency, one controlled Clear Library flow, receipt
generation, and session expiry behavior without exposing user data.

## Non-goals

- handwriting OCR;
- student roster matching;
- logo upload;
- per-exam branding overrides;
- refresh tokens; and
- deleting score/result history through Clear Library.
